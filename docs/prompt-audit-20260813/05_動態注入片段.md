# 動態注入片段（由 Python 產生，不在 templates/ 裡）

> 匯出日期：2026-08-13　·　來源：`bin/review.py`、`bin/agent_note.py`、`bin/agent_tools.py`
> 這些字串**不存在於任何 .md 模板**，是執行時由程式碼組出來、填進 `{{...}}` 佔位符或
> 直接當成 system message 送出。要完整評估提示詞品質，必須連這一份一起看。

## 1. `{{SPEAKER_WARNING}}` — 聲紋不可靠警告

**來源**：`review.py` `Job.speaker_warning` / `agent_note.py build_prompt()`
**觸發條件**：實際切出的聲紋群數 > `max(使用者填的人數 × 2, 使用者填的人數 + 3)`
**注入位置**：SCAN_TASK、AGENT_TASK
**不注入的情況**：write 階段若使用者已確認講者對應（`speaker_map` 非空），此警告會被清空——
因為姓名已由 Python 直接換進逐字稿，再警告只會讓模型對可信的姓名亂加「推測」。

```markdown
> ⚠️ **聲紋分群不可靠**：使用者填 {want} 位講者，系統卻切出 {got} 群（線上會議錄音常見）。
> 逐字稿的講者標籤不可信，請改用發言內容、人稱與角色重新判斷是誰在講，
> 並在文件開頭註明「講者對應為推測」。
```

## 2. `{{CONFIRMED}}` — 已確認事實區塊

**來源**：`review.py confirmed_block()`
**注入位置**：AGENT_TASK、PARTIAL_TASK
**組成**：依使用者在網頁回答問題卡的結果，動態拼出下列 0–4 段。

```markdown
## 已確認事實（優先於逐字稿字面）

<!-- 段落 A：使用者實際點選或手填的答案 -->
**使用者已確認——這些一律照辦，不要再推測：**

- {每題一行，例如「講者3 = 王總」「APINS → APIEMS」}

<!-- 段落 B：只有在 speaker_map 非空時出現 -->
**逐字稿中的講者標籤已由 Python 直接換成真實姓名**，所以你讀到的姓名是確定的，
不必再註明「推測」。

<!-- 段落 C：未經回答、採用系統 best_guess 的部分 -->
**以下是系統推測、使用者尚未確認**——可以採用，但文件開頭必須註明「講者對應為推測」，
並且不要把推測寫成既成事實：

- {每題一行}

<!-- 段落 D：使用者按了「跳過問題」 -->
> ⚠️ 使用者選擇「跳過問題」，以上全部是系統推測。
> 文件開頭請註明「本文件未經使用者確認關鍵資訊」。

<!-- 全都沒有時 -->
（本次沒有需要確認的事項。）
```

**不走 review 流程的直呼路徑**（`agent_note.py` 單獨執行時）會改成固定文字：

```markdown
## 已確認事實

（本次未經使用者確認流程，沒有任何已確認事實——講者姓名、專有名詞、金額日期
一律依逐字稿推斷，並在文件開頭註明「講者對應為推測」。）
```

## 4. `{{WRITE_STRATEGY}}` — 分段寫入節奏（只在 tool loop 路徑注入）

**來源**：`review.py write_strategy_block()`
**注入條件**：`backend_is_api(backend) and config.agent.tool_loop == true`
**為什麼只在這裡**：Claude Code / Codex CLI 的 Write 工具**沒有 append 模式**，
注入了反而是錯的指示。

````markdown
## 寫作方式：分段寫入（重要）

`write_file` 有兩種 mode：

- `mode="overwrite"`（預設）— 覆蓋整個檔案
- `mode="append"` — 接在既有內容後面，兩段之間自動空一行

**你的單次回覆長度有限，但檔案長度沒有限制。** 來源約 {source_chars:,} 字，
上面那條內容量要求靠單次 write_file 是寫不完的，分次寫才寫得到。
請照下面的節奏寫 `{第一份 note}.md`（其餘 `.md` 同理）：

1. `write_file(path="note_general.md", mode="overwrite")` — 先寫「本次會議重點」與「議題討論」的前 2–3 個議題
2. `write_file(..., mode="append")` — 接著寫下一批議題，一次 2–3 個
3. 議題有幾個就寫幾個，需要幾次 append 就呼叫幾次，不要合併或省略議題
4. `write_file(..., mode="append")` — 最後接上「決議事項」之後的所有章節

每次 write_file 都會回報該檔目前的總字元數，用它確認進度；
不必為了 append 而重讀檔案，也不要重寫已經寫好的段落。
`action_items.json` 與 `INDEX.md` 各自用 overwrite 一次寫完（JSON 不能 append）。
````

## 4.5 `{{SCALE_CONTRACT}}` — 內容量硬規格（三條路徑都注入）

**來源**：`agent_note.py scale_contract_block()`
**注入位置**：AGENT_TASK 的 `{{SCALE_CONTRACT}}`（路徑 A／B，由 `review.py` 與
`agent_note.build_prompt()` 各自填入）＋ `build_api_writer_prompt()` 的檔案清單之後（路徑 C）。
**為什麼獨立於 `{{WRITE_STRATEGY}}`**：「要寫多少」跟「怎麼把它寫進檔案」是兩件事。
append 機制只有 tool loop 適用，但「不要把一場會壓成摘要」對三條路徑都成立——
原本這句寄生在 write strategy 裡，等於路徑 A／C 全篇只剩禁令、沒有任何下限。

```markdown
## 內容量（硬規格）

來源約 {source_chars:,} 字。會議記錄的份量要與會議實際討論相稱——把一場會壓成幾行摘要視同失敗。

- 逐字稿裡討論到的議題，有幾個就寫幾個；不要為了篇幅合併、跳過，或只留一個標題。
- 每個議題都要寫到規格要求的深度（討論內容、誰提的、結論與依據），不要一句話帶過。
- 寫到後段覺得篇幅變長時，該做的是繼續寫完，不是把剩下的議題濃縮成摘要。
- 這條與「禁則」不衝突：禁則管的是不要編造，這條管的是不要偷懶。逐字稿沒講的仍然一律不准寫。
```

**路徑 C 專屬的補充**（加在回傳格式規則的最後一條）：它沒有 append，
回覆一旦在物件中途被 `max_output_tokens` 截斷就整份解析失敗，所以必須先講清楚讓步順序。

```markdown
- 整個 JSON 必須完整閉合。真的寫不下時，先縮減 `action_items.json` 的附屬欄位，
  最後才動議題討論——但絕不可回傳斷在一半的 JSON。
```

## 5. `WRITER_SYSTEM` — tool loop 的 system message

**來源**：`review.py:729`　**使用者**：只有 API + tool loop 路徑。CLI 路徑沒有 system message。

```text
你是一個會使用工具的文件撰寫 agent。你有 read_file、write_file、list_files 三個工具。
你必須實際呼叫工具來讀取來源檔案並寫出成品，不能只在對話中描述你要做什麼。
讀長檔案時用 offset/limit 分段讀完，不要只讀開頭就動筆。
寫長文件時用 write_file 的 mode="append" 分成多次寫完，
**不要為了塞進一次回覆而把內容壓縮成摘要**。全部寫完後，用一句話回覆表示完成。
```

## 6. 工具描述（tool schema 內的 description，模型看得到）

**來源**：`bin/agent_tools.py TOOLS`

| 工具 | description |
|---|---|
| `read_file` | 讀取一個檔案的內容。檔案很長時用 offset/limit 分段讀，回傳結果會告訴你總行數以及是否還有後續。 |
| `write_file` | 把內容寫入 job 資料夾裡的檔案。mode='overwrite'（預設）覆蓋整個檔案；mode='append' 接在既有內容後面，兩段之間自動空一行。長文件請分段寫：第一次用 overwrite 寫開頭幾節，之後用 append 一節一節接上，**不要為了塞進單次回覆而把內容壓縮成摘要**。`.json` 檔必須一次寫完，不能 append。 |
| `list_files` | 列出 job 資料夾裡現有的檔案，用來確認自己已經寫了哪些。 |

參數說明：`path`（絕對路徑或相對於 job 資料夾的路徑）、`offset`（起始行號，從 1 開始，預設 1）、
`limit`（要讀幾行，預設 400）、`content`（這一段要寫入的內容）、
`mode`（overwrite=覆蓋整份（預設）；append=接在既有內容後面）。

## 7. 續寫催稿訊息（tool loop 第 2、3 輪）

**來源**：`review.py run_writer_tool_loop()`
**觸發**：第一輪跑完後檔案缺失，或產出「太短」（`thin_notes`，門檻 `note_min_ratio` 預設 0.15）。
最多 3 輪，仍不足則印警告照現況交付。

```markdown
你上一輪還沒有把工作做完。

<!-- 缺檔時 -->
**還缺少下列檔案**，請用 write_file 補齊：
- {檔名}

<!-- 太短時 -->
下列文件**寫得太短，明顯還沒寫完**（來源約 {source_chars:,} 字）：
- {檔名}：目前只有 {size:,} 字元，至少應有 {floor:,} 字元

請用 `write_file(path=..., mode="append")` **接續**寫下去：把還沒寫到的議題、討論細節、
決議與待辦補上。**不要用 overwrite 重寫整份**，那會抹掉你已經寫好的內容；
也不要只是把現有內容換句話說。

請先用 list_files 確認現況，需要時用 read_file 重讀來源，然後動手補完。

原始任務說明如下，規格與禁則一律照舊：

{完整的 AGENT_TASK prompt 再貼一次}
```

## 9. `{{DELIVERABLES}}` — 交付清單

**來源**：`review.py run_writer()` / `agent_note.py build_prompt()`，依 `meta.json` 的
`meeting_type` 展開 `NOTE_STEMS`。

```markdown
- `note_general.md` — 一般討論會議記錄
- `action_items.json` — 決議／待辦／風險／關鍵數字（結構化）
- `INDEX.md` — 檔案清單與機密層級
```

`meeting_type = client` 時展開為 `note_client.md` / `note_self.md` / `note_partner.md` /
`email_draft.md`；`interview` 時為 `note_interview.md`。
