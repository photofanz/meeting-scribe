# meeting-scribe 提示詞總覽與體檢

> 匯出日期：2026-08-13　·　專案：`~/Meetings`
> 目的：把「產出會議記錄」所依賴的**全部**提示詞攤開，供評估是否合適。

## 一、檔案清單

| 檔案 | 對應原始檔 | 在流程中的角色 |
|---|---|---|
| `01_SCAN_TASK_掃描階段.md` | `templates/SCAN_TASK.md` | 第一階段：清稿＋產生問題卡 |
| `02_PARTIAL_TASK_分段素材.md` | `templates/PARTIAL_TASK.md` | 超長會議專用：分段抽素材（map） |

## 二、Pipeline：哪個提示詞在什麼時候跑

```
音檔
 └─ Whisper 轉寫 + 聲紋分離 ────────────────► transcript.md（無提示詞，純 ASR）
     │
     ├─【階段 1：scan】依「講者換人」切段，每段 14,000 字，最多 3 段並行
     │   提示詞 = SCAN_TASK.md
     │       ＋ {{SPEAKER_WARNING}} {{USER_CONTEXT}} {{CONTEXT}} {{BODY}}
     │   產出 = 每段一個 JSON：draft / replacements / speakers / questions
     │       └─► transcript_draft.md ＋ questions.json
     │
     ├─ 使用者到網頁點選回答問題卡 ──────────► answers.json
     │   （Python 端 deterministic 套用，不經模型）
     │       └─► transcript_clean.md（講者換名、錯字取代、修正對照表）
     │
     ├─【分岔】清稿後字數 > 60,000？
     │   是 →【map】PARTIAL_TASK.md 逐段抽素材 → materials bundle 當成唯一資料來源
     │   否 → 直接把 transcript_clean.md 當來源
     │
     └─【階段 2：write】
         提示詞 = AGENT_TASK.md
             ＋ {{CONFIRMED}} {{SPEAKER_WARNING}} {{DELIVERABLES}} {{WRITE_STRATEGY}}
             ＋ 尾端附上 {{USER_CONTEXT}}
         規格由模型自己 Read `NOTE_SPECS.md` 取得（CLI/tool loop 路徑）
         產出 = note_*.md ＋ action_items.json ＋ INDEX.md ＋ agent_report.json
             └─► Python 轉 PDF / Word（make_pdf.py / make_docx.py）
```

## 三、三條執行路徑，提示詞組合不同（很重要）

| 路徑 | 觸發條件 | 提示詞組合 | 規格怎麼拿到 |
|---|---|---|---|
| **A. CLI agent**（Claude Code / Codex） | `backend = claude`（目前預設） | AGENT_TASK 全文，無 system message | 模型自己 Read `NOTE_SPECS.md` |
| **B. API + tool loop** | `backend = openai_compat` 且 `tool_loop = true`（private 保密模式） | AGENT_TASK ＋ `{{WRITE_STRATEGY}}` ＋ `WRITER_SYSTEM` system message ＋ 缺件/太短時的催稿訊息 | 模型自己 `read_file` 規格 |
| **C. API 無工具** | API backend 但 `tool_loop = false` | **完全不同的一份 prompt**（`build_api_writer_prompt()`），規格全文、meta、逐字稿全部內嵌，要求單一 JSON 信封回傳 | 內嵌在 prompt |

**路徑 C 的提示詞與 A/B 是兩套獨立的文案**，維護時很容易只改一邊。

## 四、我對現行提示詞的體檢意見

### 寫得好的地方

1. **階段切分乾淨**：scan 只做清稿與提問、write 只做撰寫，職責不重疊。
2. **禁則具體且可驗證**：「數字照原文不換算」「沒討論寫未討論」「不得編造姓名」都是可查核的行為，不是空話。
3. **問題卡的設計克制**：明確列出「不要問」的三類（自己讀得懂的錯字／不影響結論的細節／需要打長字的問題），避免問題洪水。
4. **CONFIRMED 區塊的優先權宣告**：「已確認事實優先於逐字稿字面」是對的層級設計。
5. **推測與事實分離**：`speaker_map`（已確認）vs `speaker_guess`（推測）在提示詞裡走不同措辭，且推測必須在文首註記。

### 我認為有問題的地方

| # | 問題 | 位置 | 影響 |
|---|---|---|---|
| 1 | **全篇是抑制性禁令，沒有一條深度要求** | AGENT_TASK「禁則」6 條全是「不得…」；NOTE_SPECS 的 general 規格只定義骨架 | 小模型在高壓抑制訊號下選最安全解：全部寫「待定」、每個議題兩行。Claude 版的豐富度是它自己超額發揮，**規格並不保證** |
| 2 | **NOTE_SPECS 沒有規定「每個議題要多深」** | `04` 的 general 章節 | 「討論內容：各方提出的論點，標明是誰提的」沒有下限，一條也算數 |
| 3 | **沒有要求引用原文** | 只有 `interview` 型別要求逐字語錄，`general` 沒有 | 討論內容容易被寫成抽象概括，失去可回查性 |
| 4 | **「結論：已決議／待定／保留」沒有判定準則** | `04` general | 模型不知道什麼叫「已決議」，保守起見一律寫「待定」 |
| 5 | **`{{WRITE_STRATEGY}}` 只在路徑 B 注入** | `review.py` | 路徑 A（Claude CLI）沒有分段寫入的節奏指示——目前靠 Claude 自己夠強，但這是運氣不是設計 |
| 6 | **路徑 C 的 prompt 是獨立文案** | `agent_note.py build_api_writer_prompt()` | 改 AGENT_TASK 不會同步到它；且單一 JSON 信封先天脆弱（一個括號毀掉整份） |
| 7 | **AGENT_TASK 的「步驟」與 NOTE_SPECS 的「共同前置步驟」部分重疊且措辭不同** | `03` 步驟 1-5 vs `04` 開頭 | 兩份都說要寫 `transcript_clean.md`，但 AGENT_TASK 又禁止寫它——規格自身有內部矛盾（實際上 Python 端寫，`04` 那段是舊敘述沒清乾淨） |
| 8 | **`meeting_type` 只有 general 被實際使用** | `04` 的 client / interview 章節 | 規格文字量大但多數未驗證過，佔用模型注意力 |

### 具體建議（依 CP 值排序）

**B1｜在 NOTE_SPECS 的 general 章節加「深度契約」**（成本最低，預期效益最大）
```markdown
**深度要求（硬規格）**：
- 每個議題的「討論內容」至少 3 條，每條標明是誰提的
- 關鍵主張要引逐字稿原文（用「」括起，附 [HH:MM:SS]）
- 「結論」三選一並說明依據：
  - 已決議 = 會中有人明確拍板且無人反對
  - 待定 = 有討論但未拍板
  - 保留 = 有人明確表示要延後或反對
- 議題數量應與會議長度相稱；一小時會議少於 5 個議題請自我檢查是否漏抓
- 聽不清楚標「（音檔不清楚）」，不要整段省略
```

**B2｜修掉 `04` 的內部矛盾**：刪掉「共同前置步驟 1. transcript.md → transcript_clean.md」那段，
它已經由 Python 端完成，留著只會讓模型困惑。

**B3｜把 `{{WRITE_STRATEGY}}` 的「內容量要與會議相稱」那句抽出來，三條路徑都注入**
（分段寫入的機制只有 B 適用，但「不要壓縮成摘要」的要求對三條路徑都成立）。

**B4｜路徑 C 改成引用同一份 AGENT_TASK**，只替換工具相關段落，避免兩套文案分岔。

**B5｜精簡 client / interview 章節**，或拆到獨立 spec 檔按 `meeting_type` 動態載入，
讓 general job 的模型不必讀不相干的規格。

## 五、關鍵設定值（影響提示詞行為）

| 設定 | 目前值 | 作用 |
|---|---|---|
| `agent.backend` | `claude` | 預設走路徑 A |
| `profiles.private` | `openai_compat` + `unsloth/muse-glimmer-30b` + `tool_loop: true` | 保密模式走路徑 B |
| `chunk_chars` | 14,000 | scan/map 每段字數 |
| `chunk_overlap_turns` | 3 | 每段前面帶 3 輪上下文（僅供理解，不寫進 draft） |
| `max_parallel` | 3 | 同時跑 3 段 |
| `mapreduce_threshold_chars` | 60,000 | 超過就先走 PARTIAL_TASK 抽素材 |
| `note_min_ratio` | 0.15 | 產出/來源字數比低於此值視為「沒寫完」，觸發續寫（最多 3 輪） |
| `timeout_sec` | 3,600 | 單次呼叫上限 |
| `api.temperature` | 0.1 | API 路徑 |
| `api.max_output_tokens` | 16,384 | API 路徑單次回覆上限 |
